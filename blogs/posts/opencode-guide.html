OpenCode: What It Is, What Makes It Different, and How to Use It From Your Phone

OpenCode is an open-source AI coding agent that runs in your terminal, as a desktop app, or in a browser tab — and because it's built as a client talking to a server, you can drive a session on your laptop from your phone while walking the dog.

What OpenCode actually is

OpenCode is an open-source AI coding agent. You point it at a project, describe what you want, and it reads files, greps through the repo, runs commands, edits code, and iterates until the task is done — the same shape of tool as Claude Code, Codex CLI, or Gemini CLI.

What makes it structurally different is where it runs. The agent logic lives in a background server, and every interface — the terminal UI, the desktop app, the web app, the mobile app — is just a client connected to that server. That one architectural decision is why the phone workflow later in this post is a first-class feature rather than a hack.

✓ OpenCode is provider-agnostic. It reads model metadata from models.dev, so you can point it at Anthropic, OpenAI, Google, OpenRouter, a local Ollama or LM Studio instance, or any OpenAI-compatible endpoint — and switch per session with /models.

Installing it

A few supported paths, depending on how you like to manage tools:

# curl installer
curl -fsSL https://opencode.ai/v2/install | bash

# Homebrew
brew install anomalyco/tap/opencode-v2

# npm
npm install -g @opencode/cli

Then cd into a project and run opencode to open the full-screen TUI. Pass a path to work somewhere else: opencode ~/code/my-project. For scripts and CI, opencode run "Explain this repository" submits a prompt without opening the interactive interface, and opencode mini gives you a lighter-weight interactive mode when the full TUI is overkill.

The architecture that makes the rest possible

By default OpenCode discovers or starts one shared background server per user account. The TUI, desktop app, and web UI all attach to it. That server owns sessions, configuration, plugins, permissions, and tool execution — which means a session you started in the terminal can be picked up from another client without copying any state around.

You can check on it and restart it when things get weird:

opencode service status
opencode service restart

# a private server just for this run, to isolate problems
opencode --standalone

There's also an HTTP API with an OpenAPI spec at /openapi.json, callable from the CLI with opencode api get /api/info. If you want to build tooling on top of OpenCode — a Slack bot, a dashboard, a CI integration — that's your entry point, and there's a generated TypeScript client for it.

Features that actually matter day to day

Model freedom, including local models

This is the headline. Because the provider layer is configurable, you can run an expensive frontier model for architecture work and a cheap fast one for boilerplate, in the same tool, switching in-session. Local discovery means Ollama, LM Studio, and vLLM instances show up automatically — useful when code can't leave the machine.

# pick a model for one run, without changing your default
opencode run --model anthropic/claude-sonnet-4-5 "Refactor parseToken"

# reasoning effort variants, where the model exposes them
opencode run --model openai/gpt-5.2#high "Review this migration plan"

Defaults live in opencode.jsonc, so a repo can pin the model that suits it.

Agents: built-in roles plus your own

OpenCode ships four visible agents: Build (the default coding agent), Plan (explores and plans without editing project files), General (a broad-access subagent for research and multi-step work), and Explore (read-only search across code and web). The Plan/Build split is genuinely useful — you get a reviewed approach before anything is rewritten.

Custom agents are just Markdown files. This one adds a read-only reviewer that the main agent can launch:

---
description: Reviews changes for correctness and regressions
mode: subagent
model: anthropic/claude-sonnet-4-5#high
permissions:
  - action: edit
    resource: "*"
    effect: deny
  - action: shell
    resource: "*"
    effect: deny
---

Review the current changes. List findings in severity order
with file and line references.

Drop it in .opencode/agents/reviewer.md for the project, or ~/.config/opencode/agents/ globally. Subagents run in separate child sessions with fresh context, in the foreground or background — so "have a second agent audit what the first one just wrote" is a supported pattern, not a prompt trick.

Permissions you can actually reason about

Permissions are ordered rules with allow, ask, or deny, matched against an action and a resource. The last matching rule wins, so you put broad rules first and exceptions after:

"permissions": [
  { "action": "shell", "resource": "*", "effect": "ask" },
  { "action": "shell", "resource": "git status", "effect": "allow" },
  { "action": "read",  "resource": ".env*",      "effect": "deny" }
]

You can scope this per agent, which is how you build a reviewer that physically cannot edit files rather than one you've merely asked not to.

Skills, commands, MCP, and plugins

  • Skills — reusable instruction bundles loaded on demand, so a long runbook doesn't sit in the system prompt on every turn.
  • Commands — named prompts you invoke like CLI verbs, shareable through the repo.
  • MCP servers — add external tool servers with opencode mcp add, remote servers use OAuth by default, so no API keys copied into config.
  • Plugins — JavaScript/TypeScript hooks into tool calls, transforms, and the TUI itself. This is the layer Claude Code's hook system doesn't quite reach, because you can reshape the interface, not just intercept events.

Terminal polish that saves real time

LSP integration gives the agent actual type information and diagnostics instead of guessing from text. Formatters run automatically after edits. Snapshots let you rewind a session. Compaction keeps long sessions from falling off a cliff when context fills up. And the config is a real JSONC file with a published schema, so your editor validates it — themes and keybinds live separately in cli.json.

OpenCode vs Claude Code

I use both. They overlap heavily in capability now, so the differences come down to philosophy rather than features. Both read your repo, edit files, run commands, support MCP, support subagents, and support project-level instruction files.

Where Claude Code still wins: onboarding. Install it, log in, and you're working in two minutes with a model that's been tuned alongside the harness. Nothing to configure, no provider accounts to wire up, and the agent behaviour is extremely well polished because Anthropic controls both halves of the stack.

Where OpenCode wins: when you don't want a single vendor between you and your code. Swapping models per task, running a local model on a confidential repo, writing a plugin that changes how the interface behaves, or hosting the agent on your own machine — those are all first-class here and not really possible in Claude Code.

ℹ️ One nice wrinkle: OpenCode's Console can also serve models to Claude Code through the Anthropic-compatible endpoint, so the two aren't strictly either/or. You can keep the Claude Code harness and still route it at different models.

Using OpenCode from your phone

This is the part people don't expect. Because the agent lives in a server and the UI is just a client, your phone can be a genuine remote control for a session running on your laptop or a home server. No SSH app, no tmux, no squinting at a terminal.

Option 1: pair locally (same network / same machine)

Run opencode pair on the machine doing the work:

$ opencode pair

  Open a link to connect. Links work once and expire in 5 minutes.

  http://127.0.0.1:49374/auth/connect/...

You get a one-time link and a QR code. Scan it with the OpenCode app, or paste the link into the app's server address field. Opening it in a browser signs that browser in with a session cookie. Sessions last 30 days, and changing the server password signs every session out.

The default port is 49374 on macOS, Linux, and WSL, and 45278 on Windows. Check it any time with opencode service status.

Option 2: pair over the internet

If your laptop is at home and you're not, opencode pair --remote routes through an OpenTunnel remote address:

$ opencode pair --remote

First run asks for confirmation, and it's worth reading rather than skipping:

▲  This will expose your OpenCode server to the internet.
│  Traffic is end-to-end encrypted, and access requires your
│  server password.
│
◆  Expose your server to the internet?
│  ● Yes / ○ No

Traffic is end-to-end encrypted and gated on your server password. In non-interactive contexts you need --yes to accept. Once accepted, later runs skip the prompt — including after you turn remote access back off with opencode service set remote false, so don't assume that flag re-arms the confirmation.

Option 3: SSH port forward (my default)

If you already have SSH into the box, this is the least surprising option. The server listens only on localhost by default, so forward the port and open the printed link on your machine:

ssh -L 49374:127.0.0.1:49374 my-server

Then run opencode pair on the remote host and open the link locally. Nothing is exposed to the public internet, and you're reusing auth you already trust.

Option 4: an always-on server

For a genuinely remote setup — a VPS, a home lab box, a Mac mini in a cupboard — run the server in the foreground so a supervisor can manage it:

opencode serve --hostname 0.0.0.0 --port 4096

server listening on http://0.0.0.0:4096
server password <password>

Connect any client to it explicitly:

opencode --server http://127.0.0.1:4096

Or configure the shared background service instead of a one-off process:

opencode service set hostname 0.0.0.0
opencode service set port 49374
opencode service set password "a-long-secret"
opencode service set cors https://app.example.com
opencode service start

Changing a setting stops the background server, so the start at the end isn't optional.

Security checklist

  • Don't skip the password. The default is generated for you; replace it with a long one if you're exposing anything.
  • Prefer a private network over the public internet. Tailscale or WireGuard plus the SSH-forward approach beats a publicly reachable port.
  • Remember what the agent can do. An exposed OpenCode server is an exposed shell on your machine. Tighten permissions for the agents you use remotely — deny edit or shell on anything you wouldn't want run from a phone on a train.
  • Treat pair links as credentials. They're single-use and expire in five minutes, but anyone who gets one in time is you.

What I'd actually use it for

A realistic phone workflow isn't "write a feature on a train." It's the small stuff that otherwise blocks your day: kick off a dependency bump and let it run, review an agent's plan before you sit down, ask why CI is red and get a diagnosis queued up, or approve a permission prompt from the kitchen so a long refactor isn't sitting there waiting on you.

The bigger point is that the model of "agent runs on a machine, client is wherever I am" is just better than "agent and UI are the same process." Once you've used it, going back to a tool that only exists in one terminal window feels oddly constrained.

Final thoughts

OpenCode is the most interesting thing to happen to coding agents in a while, and not because of any single feature — it's because the architecture is open in all three directions that matter: open source, open to any model, and open to any client, including the phone in your pocket.

If you're already comfortable in Claude Code, I wouldn't switch for the sake of it. But if you've ever wanted to run a local model on a sensitive repo, swap models mid-task, or check on a long-running agent without being chained to your desk, it's worth a serious look. Start with the install and a single opencode pair — that's the moment it clicks.

If you're newer to this class of tool, my earlier post on Claude features every engineer should be using covers the workflow patterns that transfer to any agent, OpenCode included.
